# Расследование инцидентов (упрощённая модель)

Документ описывает, как SLeep поддерживает расследование инцидентов в рамках
MVP. Он дополняет [`product-plan.md`](product-plan.md) и заменяет прежнее
решение «Incident не входит в MVP».

## 1. Цель и границы

Аналитик SOC должен иметь возможность:

1. объединить несколько **событий** (`SecurityEvent`) — в том числе с разных
   устройств одной организации — в один **инцидент**;
2. привязать к инциденту **CVE-находки**, которые могли стать вектором атаки или
   важны как контекст;
3. увидеть автоматически построенную **хронологию**: что, где и в каком порядке
   происходило;
4. зафиксировать заметки, **вердикт** и **вывод** и закрыть инцидент.

Модель данных расширяется на один уровень:

```text
Raw record -> Event -> Incident
                         ^
              CVE finding (контекст или вероятный вектор)
```

В терминах жизненного цикла реагирования из NIST SP 800-61 Rev. 2 упрощённая
модель покрывает фазы «Обнаружение и анализ» и «Действия после инцидента»
(вывод и вердикт). Сдерживание, устранение и восстановление выполняются вне
SLeep; в инциденте их можно только описать заметками.

### Что входит

- Создание инцидента из одного или нескольких событий.
- Ручное добавление и удаление событий и CVE.
- Детерминированные подсказки связанных событий и CVE с объяснением причины.
- Хронология, собранная из событий, CVE, безопасных проверок и заметок.
- Статусы `open → investigating → closed`, вердикт и текстовый вывод.
- Изоляция по организациям на уровне API и внешних ключей БД.

### Что намеренно не входит

- SLA, эскалации, уведомления.
- Несколько ответственных, ветки комментариев, задачи и чек-листы.
- Автоматическое создание инцидентов без участия аналитика.
- Плейбуки и автоматическое реагирование на хостах (это противоречит принципу
  «никакого удалённого управления хостами»).
- Граф атаки внутри инцидента (появится после построения графа активов).
- Интеграция с внешними тикет-системами.

## 2. Термины

| Термин | Описание |
|---|---|
| Событие (`Event`) | Сгруппированная по правилам кластеризации активность на одном устройстве. Хранит ссылки на сырые записи. |
| CVE-находка (`CveFinding`) | Применимая к устройству уязвимость с доказательствами и уверенностью. |
| Инцидент (`Incident`) | Расследование аналитика: набор событий и CVE, хронология, заметки, вердикт и вывод. |
| Хронология (`Timeline`) | Упорядоченный по времени список фактов инцидента. Строится при чтении, а не хранится целиком. |
| Подсказка (`Suggestion`) | Событие или CVE, которое правило считает связанным с инцидентом, с текстом причины. |
| Вердикт (`Verdict`) | Итог расследования: подтверждён, ложное срабатывание, легитимная активность, не определено. |

## 3. Сценарий аналитика

1. На вкладке `Events` устройства `prod-web-01` аналитик видит событие
   `evt-01842` «Серия неуспешных SSH-входов» и нажимает **«Начать
   расследование»**.
2. Создаётся инцидент `INC-0001` в статусе `open`. Событие уже привязано,
   название подставлено из события, его можно изменить.
3. Блок **«Подсказки»** предлагает:
   - `evt-01845` «Успешный SSH-вход после серии неудач» — тот же источник
     `185.17.42.91`;
   - `evt-01846` и `evt-01847` — то же устройство, в пределах 2 часов;
   - `CVE-2024-6387` в `openssh-server` — компонент связан с событием типа
     `auth` на SSH, порт доступен извне.
4. Аналитик принимает подсказки, переводит инцидент в `investigating` и
   запускает безопасную проверку для `CVE-2024-6387`.
5. По хронологии видно, что успешный вход выполнен по паролю учётной записи
   `deploy` сразу после перебора. Признаков эксплуатации CVE нет. Аналитик
   меняет роль CVE с `entry_point` на `context` и пишет заметку.
6. Аналитик закрывает инцидент с вердиктом `true_positive` и выводом. Закрыть
   инцидент без вердикта и вывода нельзя.

## 4. Модель данных

Таблицы проектируются в стиле существующей схемы (ветка
`feature/postgres-persistence`): внутренние UUID, внешние идентификаторы для
API и составные внешние ключи `(organization_id, …)`, чтобы на уровне БД нельзя
было связать объекты разных организаций.

### 4.1. `incidents`

| Поле | Тип | Описание |
|---|---|---|
| `id` | `varchar(36)` PK | Внутренний UUID. |
| `organization_id` | `varchar(64)` FK → `organizations` | Владелец. |
| `number` | `integer` | Порядковый номер в организации. Внешний ID — `INC-{number:04d}`. |
| `title` | `varchar(500)` | Название. |
| `summary` | `varchar(4000)` | Краткое описание (необязательно). |
| `status` | `varchar(16)` | `open`, `investigating`, `closed`. |
| `verdict` | `varchar(32)` null | `true_positive`, `false_positive`, `benign`, `undetermined`. |
| `conclusion` | `text` null | Вывод аналитика. |
| `severity_override` | `varchar(16)` null | Ручная критичность; если пусто — вычисляется. |
| `created_by` | `varchar(36)` null FK → `users` | Автор (заполняется, когда появится аутентификация). |
| `created_at`, `updated_at`, `closed_at` | `timestamptz` | Служебные отметки. |

Ограничения:

- `UNIQUE (organization_id, number)`, `UNIQUE (organization_id, id)`;
- `CHECK status IN (...)`, `CHECK verdict IN (...)`;
- `CHECK (status <> 'closed' OR (verdict IS NOT NULL AND conclusion IS NOT NULL))`;
- `CHECK (closed_at IS NULL OR status = 'closed')`.

### 4.2. `incident_events`

| Поле | Тип | Описание |
|---|---|---|
| `organization_id` | `varchar(64)` | Для составных FK. |
| `incident_id` | `varchar(36)` | FK `(organization_id, incident_id)` → `incidents`. |
| `event_id` | `varchar(36)` | FK `(organization_id, event_id)` → `security_events`. |
| `added_at` | `timestamptz` | Когда привязано. |
| `added_by` | `varchar(36)` null | Кто привязал. |
| `source` | `varchar(16)` | `manual` или `suggestion`. |

PK `(incident_id, event_id)`. Одно событие может входить в несколько
инцидентов; интерфейс показывает это предупреждением, но не запрещает.

Для FK нужен новый `UNIQUE (organization_id, id)` на `security_events` — по
аналогии с `uq_devices_tenant_internal` из миграции `20260916_0002`.

### 4.3. `incident_cves`

| Поле | Тип | Описание |
|---|---|---|
| `organization_id` | `varchar(64)` | Для составных FK. |
| `incident_id` | `varchar(36)` | FK `(organization_id, incident_id)` → `incidents`. |
| `cve_finding_id` | `varchar(36)` | FK `(organization_id, cve_finding_id)` → `cve_findings`. |
| `role` | `varchar(16)` | `entry_point` — вероятный вектор; `context` — уязвимость на затронутом хосте без подтверждённой связи. |
| `added_at`, `added_by`, `source` | | Как в `incident_events`. |

PK `(incident_id, cve_finding_id)`.

### 4.4. `incident_notes`

Хранит то, что нельзя вычислить из других таблиц: заметки аналитика и журнал
изменений инцидента.

| Поле | Тип | Описание |
|---|---|---|
| `id` | `varchar(36)` PK | UUID. |
| `organization_id`, `incident_id` | | Составной FK → `incidents`. |
| `kind` | `varchar(32)` | `note`, `status_changed`, `event_linked`, `event_unlinked`, `cve_linked`, `cve_unlinked`, `cve_role_changed`. |
| `body` | `text` | Текст заметки или описание изменения. |
| `occurred_at` | `timestamptz` | Время факта. Для заметки аналитик может указать время в прошлом («в 10:45 заблокировали адрес на МСЭ»). |
| `created_at` | `timestamptz` | Время записи. |
| `author_id` | `varchar(36)` null | Автор. |

Записи журнала создаются в той же транзакции, что и само изменение.

### 4.5. Вычисляемая критичность

```text
severity = severity_override
        ?? max(severity привязанных событий,
               severity CVE с ролью entry_point)
```

Порядок: `critical > high > medium > low > info`. CVE с ролью `context` не
повышают критичность инцидента — уязвимость сама по себе не значит, что её
эксплуатировали. В демонстрационном сценарии критичность сначала `critical`
(из-за CVE-вектора), а после смены роли CVE на `context` становится `high`.

## 5. Хронология

Хронология строится при каждом запросе объединением четырёх источников и
сортируется по `occurred_at` (при равенстве — по типу источника в порядке
перечисления ниже).

| Источник | `kind` | `occurred_at` | `ended_at` |
|---|---|---|---|
| Привязанное событие | `event` | `first_seen_at` | `last_seen_at` |
| Привязанная CVE | `cve_detected` | `detected_at` | — |
| Безопасная проверка по привязанной CVE | `probe` | `created_at` задания | — |
| Заметка или запись журнала | `note`, `status_changed`, … | `occurred_at` | — |

Каждый элемент содержит устройство, критичность (если применимо), ссылку на
исходный объект и признак `source: system | analyst`. Это позволяет в интерфейсе
отличать факты, собранные системой, от выводов аналитика.

Хронология не хранится целиком, поэтому она всегда соответствует текущему
составу инцидента: отвязанное событие исчезает из неё, а сам факт отвязки
остаётся в журнале.

## 6. Подсказки связанных объектов

Правила детерминированные и объяснимые — тот же принцип, что у расчёта риска.
Каждая подсказка возвращается вместе со списком сработавших правил.

**Окно инцидента** — интервал от минимального `first_seen_at` до максимального
`last_seen_at` привязанных событий.

### 6.1. События

Кандидаты — события той же организации, ещё не привязанные к инциденту.

| Правило | Условие | Вес | Текст причины |
|---|---|---|---|
| `same_actor` | `actor` совпадает с `actor` привязанного события, разница во времени не больше 24 ч | 3 | «Тот же источник: 185.17.42.91» |
| `same_device_window` | То же устройство, событие попадает в окно инцидента ±2 ч | 2 | «То же устройство, в пределах 2 ч» |
| `shared_entity` | `correlation_key` содержит ту же сущность (IP, имя пользователя, имя процесса) | 1 | «Общая сущность: deploy» |

Показываются кандидаты с суммарным весом не меньше 3, не больше 10, по
убыванию веса, затем по близости ко времени инцидента.

### 6.2. CVE

Кандидаты — CVE-находки на устройствах, которые уже участвуют в инциденте.

| Правило | Условие | Вес |
|---|---|---|
| `component_matches_event` | Компонент CVE соответствует типу и содержанию события (таблица ниже) | 3 |
| `externally_exposed` | `exposure` указывает на внешний доступ, а у события внешний `actor` | 2 |
| `high_severity` | Критичность CVE `critical` или `high` | 1 |

Соответствие типа события и компонента (стартовый справочник, хранится в коде):

| Тип события | Компоненты |
|---|---|
| `auth` | `openssh-server`, `sudo`, `libpam*`, `krb5*` |
| `network` | Компонент, слушающий порт из события или `exposure` |
| `process` | Компонент, чей бинарный файл упомянут в событии |
| `service` | Компонент, совпадающий с именем сервиса (`nginx` → `nginx`) |
| `package` | Пакет, указанный в событии |

Порог — 3, лимит — 10. Роль по умолчанию для принятой подсказки — `entry_point`,
если сработало `component_matches_event`, иначе `context`.

Ограничение MVP: у событий нет структурированного поля сущностей, поэтому
`shared_entity` и сопоставление компонентов работают по токенам
`correlation_key`, `actor` и `summary`. После появления нормализованных
сущностей правила переводятся на них без изменения API.

## 7. Жизненный цикл

```text
open -> investigating -> closed
open -> closed            (сразу, например как false_positive или benign)
closed -> investigating   (переоткрытие)
```

| Переход | Условие |
|---|---|
| `open → investigating` | Нет. |
| `open/investigating → closed` | Заполнены `verdict` и `conclusion`. Ставится `closed_at`. |
| `closed → investigating` | Вердикт и вывод сохраняются, `closed_at` очищается. |

Каждый переход записывается в `incident_notes` с `kind = status_changed`.
Изменять состав закрытого инцидента нельзя: сначала его нужно переоткрыть.

## 8. API

Все маршруты требуют `X-Organization-ID` (временная граница до появления
аутентификации) и возвращают только объекты своей организации. Чужой или
несуществующий объект — `404`. События и устройства адресуются внешними
идентификаторами, как в существующем API.

| Метод и путь | Назначение |
|---|---|
| `GET /v1/incidents?status=&severity=` | Список инцидентов. |
| `POST /v1/incidents` | Создать инцидент из событий и CVE. |
| `GET /v1/incidents/{incident_id}` | Карточка: поля, события, CVE, устройства. |
| `PATCH /v1/incidents/{incident_id}` | Изменить название, описание, статус, вердикт, вывод, ручную критичность. |
| `POST /v1/incidents/{incident_id}/events` | Привязать событие. |
| `DELETE /v1/incidents/{incident_id}/events/{event_id}` | Отвязать событие. |
| `POST /v1/incidents/{incident_id}/cves` | Привязать CVE. |
| `PATCH /v1/incidents/{incident_id}/cves/{device_id}/{cve_id}` | Изменить роль CVE. |
| `DELETE /v1/incidents/{incident_id}/cves/{device_id}/{cve_id}` | Отвязать CVE. |
| `GET /v1/incidents/{incident_id}/timeline` | Хронология. |
| `POST /v1/incidents/{incident_id}/notes` | Добавить заметку. |
| `GET /v1/incidents/{incident_id}/suggestions` | Подсказки событий и CVE. |
| `GET /v1/devices/{device_id}/events/{event_id}/incidents` | Инциденты, в которые входит событие (для предупреждения в интерфейсе). |

Коды ошибок: `404` — объект не найден в организации; `409` — изменение
закрытого инцидента или повторная привязка; `422` — нарушение правил перехода
(например, закрытие без вердикта).

## 9. Интерфейс

- В боковой навигации появляется раздел **«Расследования»** рядом с
  «Устройствами»: таблица с номером, названием, статусом, критичностью,
  устройствами, временем активности и вердиктом.
- На вкладке `Events` у каждого события есть действия **«Начать
  расследование»** и **«Добавить в расследование»**. Если событие уже входит в
  инцидент, рядом показывается его номер.
- В карточке CVE есть действие **«Добавить в расследование»**.
- Страница инцидента:
  - шапка: номер, название, статус, критичность (с пометкой «вычислена» или
    «задана вручную»), вердикт, кнопки смены статуса;
  - слева — **хронология**: вертикальная лента, интервалы событий показаны
    отрезками, у элементов есть метка устройства, записи аналитика визуально
    отличаются от системных;
  - справа — вкладки **«События»**, **«CVE»** (с переключателем роли),
    **«Подсказки»** (с причинами и кнопками «Добавить» и «Скрыть»);
  - снизу — поле заметки с необязательным временем факта.
- Закрытие открывает диалог с выбором вердикта и обязательным выводом.

## 10. Демонстрационный сценарий

Для демонстрации в seed добавляются три события на `prod-web-01` и инцидент
`INC-0001`. Время указано относительно дня демонстрации.

| Время | Источник | Факт |
|---|---|---|

## 11. Критерии готовности

- Инцидент создаётся из одного или нескольких событий, в том числе с разных
  устройств одной организации.
- Нельзя привязать событие или CVE другой организации — ни через API (`404`),
  ни напрямую в БД (нарушение FK).
- Хронология отсортирована по времени, включает все четыре источника и сразу
  отражает отвязку объектов.
- Подсказки детерминированы: одинаковые входные данные дают одинаковый
  результат с одинаковыми причинами.
- Нельзя закрыть инцидент без вердикта и вывода — ни через API (`422`), ни в БД
  (`CHECK`).
- Нельзя изменить состав закрытого инцидента (`409`).
- Каждое изменение статуса, состава и роли CVE оставляет запись в журнале.
- Миграции проходят на SQLite и PostgreSQL (тест `test_migrations`).

## 12. Этапы реализации

1. **Схема.** Миграция `0004`: `UNIQUE (organization_id, id)` на
   `security_events`, таблицы `incidents`, `incident_events`, `incident_cves`,
   `incident_notes`. Модели SQLAlchemy и Pydantic.
2. **API.** CRUD инцидента, привязки, переходы статусов, журнал. Тесты на
   изоляцию организаций и правила переходов.
3. **Хронология.** Сборка из четырёх источников, тесты сортировки и отвязки.
4. **Подсказки.** Правила из раздела 6, справочник компонентов, тесты
   детерминированности.
5. **Seed.** Три новых события и демонстрационный инцидент из раздела 10.
6. **Интерфейс.** Раздел «Расследования», страница инцидента, действия на
   вкладках `Events` и `CVE`. Требует перевода интерфейса с захардкоженных
   данных на API.
7. **Отчёт (по возможности).** Выгрузка инцидента в Markdown или PDF:
   поля, хронология, вывод.
